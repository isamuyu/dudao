## 1. 引言

### 1.1 编写目的

本文档定义"基于地理位置的全国无障碍督导系统"的功能需求、数据需求、非功能需求与接口需求，作为产品设计、开发、测试和验收的依据。目标读者包括：项目管理人员、产品经理、架构师、开发工程师、测试工程师、业务专家（无障碍督导员代表）。

### 1.2 项目背景

- GB 55019-2021《建筑与市政工程无障碍通用规范》为全文强制性工程建设规范，自 2022 年 4 月 1 日起施行，其全部条文为强制性条文；GB 50763-2012《无障碍设计规范》作为补充参考继续有效。
- 无障碍环境建设涉及新建、改建、扩建的建筑与市政工程，覆盖面广、点位分散、问题类型多样，传统人工纸质督导方式存在**底数不清、标准不一、取证困难、整改无闭环、统计靠手工**等问题。
- 督导业务通常由**各地组织（残联、督导队、第三方机构等）分区域承接**：不同组织之间数据需要隔离，同一组织内部需要协同，组织只能在授权区域内开展督导。系统须以多租户方式支撑该业务模式。
- 各地无障碍督导员在现场检查时，需要随时对照"该类建筑应配置哪些无障碍设施、每项设施的技术参数是多少、依据哪一条规范条款"，缺乏随身、结构化、可定位的数字化工具。
- 因此需要建设一套**以地理位置（GIS）为核心组织方式**、以国家强制性规范条款为判定依据、以**组织（租户）为数据隔离单元**的全国无障碍督导系统，实现"点位上图、清单随查、现场取证、问题闭环、数据归集"。

### 1.3 术语与定义

| 术语 | 定义 |
| --- | --- |
| 组织（租户） | 系统中独立的数据隔离单元，如某地残联督导队、第三方督导机构；组织间数据互不可见 |
| 组织管理员 | 组织内的管理角色，负责设定检查点建筑（点位）、创建与分配任务、管理本组织用户 |
| 督导员 | 组织内执行现场检查、录入问题并跟踪整改的人员 |
| 督导区域 | 组织被授权开展督导的行政地理范围（可精确到省/市/区县，或自定义地理围栏），组织只能督导该区域内的点位 |
| 点位（POI） | 地图上具有唯一地理坐标的被督导对象，由组织管理员预先设定，其位置与建筑类别在督导任务中固定 |
| 设施实例 | 一个点位下按设施类别拆分出的具体被检对象（如"南门东侧出入口""1 号楼无障碍电梯"），同一类设施存在多个时可逐个增加实例分别检查 |
| 配置清单 | 依据 GB 55019-2021 与 GB 50763-2012 编制的"各类建筑无障碍设施配置清单表格"，是现场核查的判定依据 |
| 检查项 | 清单中的最小核查单元，由"建筑类型 × 设施类别"组合生成，含配置等级、具体要求、条款依据 |
| 配置等级 | ● 必须设置（强制性底线要求）；○ 条件设置（满足规定条件时应配置）；△ 推荐设置（宜配置）；— 不适用 |
| 问题单 | 一次现场检查中发现的不符合项记录，是整改闭环管理的基本单元 |
| G19 | GB 55019-2021《建筑与市政工程无障碍通用规范》 |
| G63 | GB 50763-2012《无障碍设计规范》（补充参考） |
| 重点配置对象（★） | 应全面配置无障碍设施并满足高标准要求的建筑类型，如政府/行政办公、大中型医疗、康复中心、交通建筑、图书馆、博物馆、体育场/馆等 |

## 2. 项目概述

### 2.1 产品定位

面向全国无障碍督导业务的**移动优先、GIS 驱动、多租户**督导检查与整改闭环平台。由移动端 App（督导员现场使用）+ Web 管理端（组织管理员/管理部门使用）+ 服务端平台三部分构成。

### 2.2 多租户组织模型（核心约定）

1. **组织即租户**：每个组织（如某地无障碍督导队）是独立租户，组织之间的点位、任务、检查记录、问题单、统计数据**完全隔离、互不可见**。
2. **组织内数据互通**：一个组织下可有多个用户（组织管理员 + 若干督导员），同一组织内的点位台账、任务、检查记录、问题单对本组织用户按角色共享可见，支持协同。
3. **组织有区域限制**：每个组织绑定一个或多个督导区域（行政区划或地理围栏）。组织只能查看、设定和督导其区域范围内的点位；跨区域操作被系统拒绝。平台级管理员可跨组织进行全局统计（脱敏后）。
4. **角色体系**：

| 角色 | 所属层级 | 说明 | 主要使用端 |
| --- | --- | --- | --- |
| 平台管理员 | 平台 | 组织开通、区域授权、全局字典与检查项库维护、跨组织脱敏统计 | Web |
| 组织管理员 | 组织 | **设定检查点建筑（位置、类别固定）**、创建/分配任务、审核问题单、管理本组织用户、查看本组织统计 | Web + App |
| 督导员 | 组织 | **领取任务**、现场检查、录入问题、复查整改 | 移动端 App |
| 整改责任单位 | 组织关联 | 接收整改通知、反馈整改结果（仅见与本单位相关的问题单） | Web / 轻量移动端 |
| 公众用户（二期） | — | "随手拍"上报无障碍问题线索 | 小程序 |

### 2.3 建设目标

1. **点位上图**：各组织将被督导对象以地图点位统一管理，支持按区域、建筑类型、配置等级检索。
2. **清单随查**：内置《各类建筑无障碍设施配置清单》，按点位建筑类型自动生成现场核查表，条款依据可溯源。
3. **现场取证**：检查记录自动附加 GPS 定位、时间、照片/视频水印，证据链完整。
4. **问题闭环**：问题发现 → 派单 → 整改 → 复查 → 销号全流程线上流转，超期预警。
5. **数据归集**：组织内数据实时归集，组织看本组织、平台看全局（脱敏），支持覆盖率、问题分布、整改率等多维统计与地图热力展示。

### 2.4 建设约束与假设

- 移动端必须支持弱网/离线作业（地下空间、偏远区域），数据本地暂存、联网后同步。
- 地理位置服务在国内须使用合规地图（天地图 / 高德 / 百度），坐标系采用 GCJ-02 或 CGCS2000，并做好与 WGS-84 的转换。
- 检查判定规则以 GB 55019-2021 为底线；地方标准（如北京 DB11 系列）要求更高时从其规定，规则库须支持地方扩展包。
- 一期范围不含公众小程序与 AI 图像识别自动判定（列为二期规划）。

```
┌────────────────────────────────────────────────────────────┐
│                     Web 管理端（PC）                        │
│  组织管理 | 点位设定 | 任务管理 | 问题督办 | 统计 | 系统管理 │

│                  移动端 App（督导员）                       │
│  地图点位 | 领取任务 | 现场检查 | 拍照取证 | 问题上报 | 复查 │
├────────────────────────────────────────────────────────────┤
│                     服务端平台（多租户）                    │
│  租户/组织 | 用户权限 | GIS点位服务 | 检查项库/规则引擎      │
```

## 4. 检查业务主流程（核心逻辑）

```
组织管理员（Web/App）                    督导员（App）
─────────────────────                 ─────────────────────
① 设定检查点建筑
   - 地图选点/现场采点
   - 固定位置（GPS+地址）
   - 固定建筑大类/具体分类
   - 录入责任单位等台账信息
          │
② 创建督导任务（选点位、定时限）
          │
          ▼
                              ③ 领取任务（任务池/被指派）
                                     │
                              ④ 到达现场 GPS 签到
                                     │
                              ⑤ 录入建筑主体信息
                                （名称核实、门脸/全景照片、
                                  楼层数、建设性质、联系人、
                                  采集状态等）
                                     │
                              ⑥ 系统按建筑类别生成核查表
                                （配置矩阵自动匹配）
                                     │
                              ⑦ 逐项检查：
                                - 适用性判断（是/不适用）
                                - 数值实测自动判定 / 人工判定
                                - 拍照取证
                                - 同类设施存在多个子项时，
                                  动态增加"设施实例"分别检查
                                  （如 3 个出入口、2 部电梯）
                                     │
                              ⑧ 提交检查记录，自动生成
                                检查报告 + 不符合项问题单
                                     │
          ┌──────────────────────────┘
          ▼
组织管理员审核问题单 → 派单整改 → 责任单位反馈 → 督导员复查 → 销号
```

**关键规则**：
- 点位的**位置与建筑类别由组织管理员设定后固定**，督导员不可修改（防止错用核查标准），仅能补充现场实况信息。
- 一个任务对应一个点位；一个点位下可含多个**设施实例**（同类设施多处设置时逐个增加、分别核验、分别生成不合格项）。
- 现场因施工、被占用、不允许进入等原因无法检查时，按"**无法采集 + 原因**"记录并附照片佐证，任务可结办但点位保留待下次督导。

## 5. 功能需求

> 编号约定：FR-模块号.序号。优先级：P0 一期必须，P1 一期重要，P2 二期。

### 5.1 组织（租户）与区域管理（FR-1）★核心模块

| 编号 | 需求描述 | 优先级 |
| --- | --- | --- |
| FR-1.1 | 组织开户：平台管理员创建组织租户，登记组织名称、类型（残联/督导队/第三方机构/主管部门）、联系人、有效期 | P0 |
| FR-1.2 | **区域授权**：为组织绑定督导区域（省/市/区县多级行政区划，支持自定义地理围栏绘制），区域可调整并留痕 | P0 |
| FR-1.3 | **区域限制强制生效**：组织用户只能查看、新增、督导其授权区域内的点位；地图加载、检索、任务、统计全部按区域过滤；跨区域请求服务端拒绝 | P0 |
| FR-1.4 | **租户数据隔离**：点位、任务、检查记录、问题单、文件等全部租户数据携带组织标识，任何查询强制按组织过滤；跨组织数据不可见 | P0 |
| FR-1.5 | **组织内数据互通**：同组织用户共享本组织点位台账与业务数据（按角色控制写权限），支持任务转派、协同检查、数据互相可见 | P0 |
| FR-1.6 | 组织状态管理：启用/停用（停用后用户不可登录，数据保留）；到期提醒 | P1 |
| FR-1.7 | 平台级全局视图：平台管理员可跨组织查看脱敏汇总统计，不可查看组织内部明细（除非授权） | P1 |
| FR-1.8 | 数据导出归属：组织可导出本组织全部数据；组织注销时数据归档与交接机制 | P2 |

### 5.4 检查项库与规则引擎（FR-4）★核心模块

| 编号 | 需求描述 | 优先级 |
| --- | --- | --- |
| FR-4.1 | 内置《各类建筑无障碍设施配置清单》结构化数据库（平台级全局共享）：总体配置矩阵（建筑类型 × 14 类设施 × 配置等级 ●/○/△/—）+ 各类建筑详细要求 + 关键技术参数速查表 | P0 |
| FR-4.2 | 每个检查项包含字段：建筑类型、具体分类、设施类别、配置等级、具体要求说明（含量化参数，如坡道坡度≤1:12、通道净宽≥1.20m）、条款依据（G19 §x.x / G63 §x.x）、是否重点配置对象（★） | P0 |

### 6.2 租户隔离实现要求

- 所有租户数据表强制携带 `org_id`，服务端数据访问层统一注入组织过滤条件（不允许业务代码自行拼组织条件，防越权漏过滤）；
- 跨区域/跨组织访问返回与"不存在"一致的响应，避免探测；
- 文件/影像存储按组织分桶或分前缀，访问签名校验组织归属；
- 平台级共享数据（字典、检查项库）只读下发，组织不可修改。

### 6.3 数据规模估算（供容量规划参考）

- 组织：按 500–2000 个组织规划；点位：全国按 50 万–200 万点位规划（含市政路段），单条点位含图片约 2–5 MB；
- 检查记录：年均 100 万+ 条，单条含 5–10 张照片；
- 影像存储：首年按 10 TB 规划，支持对象存储弹性扩展。

### 6.4 数据安全要求

- 检查记录、照片证据须防篡改（哈希校验/只增不改的审计日志）；
- 数据传输 HTTPS，敏感字段加密存储；
- **租户隔离为最高优先级安全要求**：任何接口不得跨组织返回数据；渗透测试须包含越权访问用例；
- 满足等级保护二级（政务环境按三级）要求。

## 9. 技术建议（非约束性）

- 移动端：Flutter 或 React Native 跨端开发（兼顾 Android/iOS），GIS 组件选用合规地图 SDK；
- Web 端：Vue3/React + 地图 JS API + ECharts 统计图表；
- 服务端：微服务或模块化单体（一期可单体起步），PostgreSQL + PostGIS（空间数据与地理围栏）+ Redis + 对象存储；
- 多租户：一期采用**共享库 + org_id 行级隔离**（配合数据库行级安全策略 RLS 兜底），大型组织可演进为 schema/库级隔离；
- 规则引擎：检查项匹配、适用性判断与数值自动判定采用配置化规则表驱动，避免硬编码条款；
- 现场审查交互可参考"居住区无障碍设施标准审查程序"的工作台模式：项目基本信息 + 设施实例清单两级页面，四步填写流程（确认信息 → 适用性判断 → 逐项核验 → 统计导出），配置驱动加载不同设施标准模板。

### 附录 D：判定效力规则

1. GB 55019-2021 为底线要求，全部条文强制；与 GB 50763-2012 不一致时按 G19 执行；G63 仅作 G19 未覆盖参数的补充参考。
2. 地方标准要求更高时从其规定（规则扩展包机制）。
3. 既有建筑改造受条件限制的，应进行无障碍专项论证并采取等效替代措施——系统问题单需支持"等效替代"结论类型。
4. 无障碍设施须系统化、连续化设置，"有设施不连通"视为问题（FR-6.8）。
